### 0.2 「覆盖」写入的数据安全（P0）

**现状**

- `transfer()` 的物理目录移动分支在 Overwrite 下先删除目标、再调用 `moveMediaStoreItem()`（`MediaRepository.kt:608-611`）。
- `tryDirectMediaStoreMove()` 在 `Overwrite` 下**先删除目标**，再调用 `moveMediaStoreItem()`（`MediaRepository.kt:822-825`）。后者本身已经实现了「先移到临时名、成功后删旧目标」的安全顺序（`:838-856`），但被前面的预删除破坏：目标已不存在，第二次删除返回 0，函数回滚并返回 `null`，调用方再走慢速复制回退。
- `moveToDocumentDirectory()` 同样先 `deleteUriPermanently(existing)` 再移动（`MediaRepository.kt:901-902`）；移动失败时旧目标已经没了。
- `moveByCopyAndPermanentDelete()` 在覆盖时也是先删 `existing`、再 rename；失败 catch 删掉 `finalUri`（`MediaRepository.kt:936-947`）。旧目标已删，新副本也被删。
- `transferToDocumentDirectory()` 在覆盖时先 `existing.delete()`，再 `renameDocument()`；`catch` 里又把刚写好的 `target` 删掉（`MediaRepository.kt:1019-1027`）。**旧目标和新副本会同时消失**（源文件还在）。
- `insertIntoMediaStore()` 在复制覆盖时先发布新行、删除旧行，再改回正式文件名；改名的 `update` 失败会进入 `getOrElse` 删除新目标（`MediaRepository.kt:779-790`）。旧目标已删、新目标也被删。
- 复制完成后没有回读校验；`TransferFailure.VerificationFailed` 枚举存在但主代码从未产生（`MediaTransfer.kt:17-24`，`MediaFileOps.kt:14-35`）。

**影响**

用户选择「覆盖」时，默认预期是「成功则替换，失败则保留原样」。现在的实现是「失败可能连原来的目标一起丢」。这是相册类应用最不可接受的数据损失类型；对移动场景，源文件通常还在，但目标位置的旧版本可能是唯一副本。

**建议**

1. 删除所有「预删除目标」；覆盖统一走「写临时名 → 校验 → 原子改名 → 删旧目标」的顺序。
2. SAF 覆盖不要删除 `existing`，先改名为 `.bak`；新文件 rename 成功后再删 `.bak`，失败只回滚新文件。
3. 复制后至少比对目标长度与源长度（已知大小时），不一致归为 `VerificationFailed` 并回滚。
4. 为 `Overwrite + MediaStore / SAF / 物理目录` 建失败注入测试：强制 rename/delete 返回失败，断言旧目标仍在、源文件仍在。
5. 验收：覆盖失败后目标目录里仍有旧文件；移动失败后源文件仍在原处；日志能说明失败步骤。

**执行进度（2026-11-21）**：已完成代码修复——移除 MediaStore/SAF 路径的预删除；`writeFileReplacing`、`moveToDocumentDirectory`、`moveByCopyAndPermanentDelete`、`transferToDocumentDirectory`、`insertIntoMediaStore` 都改为「旧目标先备份/改名 → 提交新文件 → 删备份」，失败回滚。v1.3.66 已发布（run `44874443897` 全绿）。v1.3.67 已发布（run `44877000433`），进一步把覆盖流程抽成 `OverwriteTransaction`，新增 9 个失败注入用例：MediaStore/SAF 共用的 move/commit/delete 失败、provider 抛异常、Move 源删除前保留备份；物理路径已有 `MediaFileOpsTest.keepsTheOldFileWhenItCannotBeMovedAside`。全量单测 **215 个 0 失败**，lint 通过（无新增 error/warning，2 hints）。真机（vivo V2254A，Android 16）实际执行「复制同名文件 + 覆盖」：目标被替换为源文件（`cmp=0`），源文件保留，目标目录无 `album-tmp` 残留。**T2 收口 ✅**；仍缺真实 ContentResolver/SAF provider 的集成级故障注入（当前为事务级 fake），列为后续增强。

### 0.3 首启权限与引导（P1）

**现状**

- 首次打开时，`showGestureHints` 默认置 true，直接弹出 5 条隐藏手势说明（`AlbumApp.kt:811-815`、`4073-4077`；清单见 `GestureHintsSheet.kt:31-42`）。用户还没看到一张照片，先读到「长按底栏排序」「上下滑动调亮度」。
- 审查时首启权限把 `READ_MEDIA_IMAGES`、`READ_MEDIA_VIDEO`、`READ_MEDIA_VISUAL_USER_SELECTED` 与 `POST_NOTIFICATIONS` 一起申请（`AlbumApp.kt:4609-4611`，`2169-2173`）。通知权限与「浏览本地照片」没有直接关系；v1.3.67 已从清单和首启申请中移除通知权限。
- 媒体权限授予后，`LaunchedEffect(library.permissionGranted)` 会自动打开「所有文件访问权限」系统页（`AlbumApp.kt:2174-2186`）；`permissionLauncher` 回调又会打开「媒体管理权限」系统页（`AlbumApp.kt:1940-1953`）。用户可能在几秒内被送去两个系统设置页，且没有解释。
- 「所有文件访问」对应 `MANAGE_EXTERNAL_STORAGE`（`AndroidManifest.xml:22`），是 Google Play 严格审查的权限；应用的核心浏览/整理并不需要它才能工作（MediaStore + SAF 已有回退）。

**影响**

首启信任被连续三次打断：手势说明 → 权限弹窗 → 系统设置页。用户会认为应用「要得太多」，而应用真正的本地优先卖点完全没有被解释。对 Play 上架/应用商店审核也是高风险项。

**建议**

1. 首启只申请照片/视频权限，配一页简短的价值说明（本地处理、不上传、可随时撤销）。
2. 通知权限：v1.3.67 已直接移除；后台播放/归档扫描只使用前台服务通知，不再申请运行时通知权限。
3. 删除自动跳转「所有文件访问」「媒体管理」；改为设置页的「可选权限」卡片，写清用途、拒绝后的替代路径（SAF/MediaStore）。
4. 手势提示改为「设置 → 使用提示」可随时打开；首次只在用户完成一次浏览后，以一条可关闭的轻提示出现，不要用 5 条清单堵住首屏。
5. 验收：Android 13/14 全新安装，首屏只出现一次照片/视频权限；不再申请通知权限；不跳系统设置；手势说明不再自动弹。

### 0.4 编辑器退出保护（P1）

**现状**

- `BackHandler(enabled = !saving) { leaveEditor(onDismiss) }`（`ImageEditorDialog.kt:304`）和顶栏 X 的 `onClose = { leaveEditor(onDismiss) }`（`:377`）都直接关闭，不检查 `saveEnabled`、不检查撤销栈、不弹确认。

**影响**

用户修图 10 分钟，误触返回或 X，全部丢失且无提示。相比其他数据风险，这个修复成本极低，属于「必须马上补」的体验底线。

**建议**

1. 退出时若有未保存修改，弹三选一：「保存」「丢弃」「取消」；「保存」复用现有保存流程（含替换原图确认）。
2. 系统返回与顶栏 X 走同一个 `requestClose()`；保存中禁用退出。
3. 可选：把编辑状态写入 `cacheDir` 草稿，进程被杀后下次进入提示恢复；不作为首版必需。
4. 验收：编辑一次 → 按返回 → 出现确认；点「取消」回到编辑现场；点「丢弃」才退出；点「保存」完成保存并退出。

**执行进度（2026-11-21）**：v1.3.70 已发布（run `44883031596`），把返回键与顶栏 X 统一到 `requestExit()`；有未保存修改时显示「保存并退出 / 丢弃修改 / 取消」，保存沿用原有「保留二者 / 替换原图 / 每次询问」流程，保存失败留在编辑器。真机验证了无修改直接退出、修改后弹确认、丢弃退出；未做草稿落盘（指南列为可选），T4 收口 ✅。

### 0.5 亮色主题对比度（P1）

**现状**

默认强调色是荧光绿 `#00E673`（`Color.kt:5`、`Theme.kt:45`）。按 WCAG 相对亮度公式计算：

- 绿字 / 白底、白字 / 绿底都是 **1.67:1**；蓝 3.31、青 2.12、橙 2.06、珊瑚 3.41、紫 4.13；次要文字 `#717975` 为 4.47:1。全部低于 4.5:1（逐色表见 4.1）。
- 实际使用点：底栏选中标签 11sp、顶部模式胶囊 14sp（`VaultTopBar.kt:93-96`）、编辑器「完成」白字绿底（`ImageEditorDialog.kt:765-772`）、底栏选中色（`AppBottomBar.kt:156-162,243-249`）。这不是某个页面没调好，而是**默认 token 在亮色主题下整体不可读**。

**建议**

1. 把「强调色」拆成三层：`accent`（装饰/填充）、`accentText`（亮色主题下用于文字/图标）、`onAccent`（填充上的文字）。亮色主题下绿色文字建议改为 `#007A3D` 左右（对白底约 5.0:1），或采用「浅色底 + 深色字」的胶囊，而不是荧光绿字。
2. 对 6 个强调色逐个计算亮/暗两套对比度，写进设计 token 注释与测试；编辑器「完成」在亮色下改用深色字或深绿底。
3. 验收：所有强调色文本 ≥4.5:1；白字按钮 ≥4.5:1；截图/脚本检查通过；TalkBack 用户不依赖颜色也能识别选中态（补 `stateDescription`）。

**执行进度（2026-11-21）**：v1.3.71 已发布（run `44884516663`）。亮色主题的 6 个强调色在主题层自动加深到白底 ≥4.5:1；暗色主题保留原色；编辑器「完成/确认」改用 `onPrimary`；次要文字由 `#717975` 加深到 `#6B736F`。新增 `ThemeContrastTest` 3 个用例，逐一校验 6 个强调色的文字、白字按钮和次要文字对比度；全量单测 **218 个 0 失败**。真机安装 1.3.71 检查了相册页/设置页的深绿选中态。T5 收口 ✅；底栏 TalkBack 选中态 `stateDescription` 已在 v1.3.72 补上。

## 1. 宏观定位

**一句话判断：Album 是「本地优先的重度媒体工作台」，不是大众相册；它的能力密度是护城河，也是当前最大的产品风险。**

### 1.1 它是什么

README 的自我描述很准确：把 **Pixiv 本地归档与 Tag 检索**、**静态/动态壁纸队列**、**完整图片编辑**、**兼容 AVI 的视频播放**集中在同一款本地优先应用里（`README.md:19`）。这些能力不是普通相册的「附加功能」，而是四个独立工具被塞进一个 App：

| 能力 | 代码规模/入口 | 用户价值 |
|---|---|---|
| 文件夹/时间轴浏览、批量整理 | `AlbumApp.kt` 4,681 行；`AlbumsScreen.kt` 840 行 | 日常主路径 |
| Pixiv 归档 + Tag 索引 | `PixivArchiveRepository.kt` 2,042 行；可选底栏/Tools 入口 | 差异化最强 |
| 图片编辑器（10 款字体、涂鸦、文字） | `ImageEditorDialog.kt` 3,585 行；`ImageEditorEngine.kt` 949 行 | 替代轻量修图 App |
| 视频播放（Media3 + LibVLC 双引擎、小窗、PiP） | `Media3VideoPlayer.kt` 1,946 行；`MediaViewer.kt` 1,437 行 | 兼容 AVI/MPEG 的刚需 |
| 壁纸/幻灯片队列 | `WallpaperManagerScreen.kt`、`WallpaperCropScreen.kt` | 展示与个性化 |
| 清理/回收站/查重 | `CleanupScreen.kt` 2,894 行；`CleanupRepository.kt` 1,167 行 | 存储治理 |

### 1.2 它不是什么

| 不是 | 原因 | 证据 |
|---|---|---|
| 云相册/账号体系 | 无后端、无账号、`allowBackup=false`；定位是本地优先 | `README.md:5-7,34`、`AndroidManifest.xml:52` |
| 社交/社区 | 无分享社区、无关注/评论；分享只是系统分享 | 代码中无相关模块 |
| 视频剪辑/NLE | 有 `media3-transformer` 依赖，但没有剪辑入口；播放器定位是「看」 | `app/build.gradle.kts` 依赖；UI 无剪辑页 |
| AI 修图/生成 | 无模型、无云端推理；编辑器是传统像素操作 | `ImageEditorEngine.kt` |
| 普通用户开箱即用 | 首屏是文件夹；54 项设置；5 条隐藏手势；Pixiv 默认隐藏 | 第 2、4 章 |
| 跨平台 | 仅 Android（minSdk 24 / targetSdk 36） | `app/build.gradle.kts:40-43` |

### 1.3 目标用户与产品阶段

**当前真实用户画像（推断，未做访谈）**：愿意自己整理文件夹、能理解「回收站/排除文件夹/归档目录」、会为了 AVI 或 Pixiv 折腾设置的人。这个人群存在，而且付费/口碑意愿不低；但它不是「给爸妈装的相册」。

**产品阶段判断**：功能完整度已经超过大多数个人相册（B+），工程与发布成熟度仍停留在「个人项目」（C/D）。决定它能否被推荐的，不是再做一个功能，而是三件事：

1. **可信的分发**：用户能拿到新版本，知道自己在装什么。
2. **不丢数据**：覆盖、删除、回收站、导入导出在失败时都可解释、可回滚。
3. **首小时可理解**：新用户能在 5 分钟内完成「看照片 → 看视频 → 删一张 → 找回」四条主路径。

达到这三点后，再谈大屏、国际化、体积和性能，才是有意义的优化。

## 2. 信息架构与主流程

### 2.1 当前 IA 地图

```
底栏（默认 4 个，Pixiv 可选）
├─ 相册（图片/视频二态）
│  └─ 文件夹网格 → 文件夹内媒体网格 → 查看器 / 编辑器
├─ 时间轴（图片/视频二态）
├─ 工具箱
│  ├─ 壁纸队列 → 裁剪 → 应用静态/动态壁纸
│  ├─ 文件清理 → 回收站 / 重复图片 / 已排除
│  ├─ 幻灯片队列 → 播放
│  ├─ Pixiv 文件归档 → 登录 → 扫描 → 归档
│  └─ SauceNAO / ascii2d 搜图
└─ 设置（界面 / 文件操作 / 显示 / 视频 / 幻灯片 / 缓存 / 关于）
```

- `MainTab` 定义 6 项：相册、视频、时间轴、Pixiv、工具箱、设置（`AlbumApp.kt:218-225`）。
- `enabledMainTabs()` 永远排除 `Videos`，Pixiv 由 `pixiv_tab_enabled` 控制（`AlbumApp.kt:256-258,551`）。所以底栏实际是 4 或 5 项。
- 顶栏的「图片/视频」胶囊切换 `albumShowsVideos` / `timelineShowsVideos`（`AlbumApp.kt:3159-3173`）；底栏的「相册」标签和图标会随这个状态变成「视频」（`AlbumApp.kt:1346-1362`）。
- 进入文件夹后底栏隐藏（`barVisible = openedFolder == null && !wallpaperManagerOpen`，`AlbumApp.kt:3245`）。
- 设置分 7 类、54 行（`SettingsScreen.kt:847-855`；`grep -c 'ToggleRow(\|ValueRow(\|ClickableRow('` = 54）。

### 2.2 主流程（按用户任务）

| 任务 | 当前路径 | 评价 |
|---|---|---|
| 看全部照片 | 相册 → 选文件夹 → 网格；或时间轴 | 时间轴是唯一全量视图；相册首屏没有「全部」 |
| 看视频 | 相册 → 顶栏胶囊切到「视频」→ 选文件夹 | 模式不可见，底栏标签会变 |
| 搜索 | 当前页搜索框；相册/时间轴/文件夹/Pixiv 各自搜索 | 无全局搜索；搜索不跨类型 |
| 整理 | 长按/拖拽多选 → 复制/移动/重命名/删除 | 能力强，但入口全靠长按和手势 |
| 删除/找回 | 删除 → 确认 → Toast；找回：工具箱 → 文件清理 → 回收站 | 无 Undo；回收站入口深 |
| 修图 | 查看器 → 编辑 → 保存 | 退出无保护；工具多但可发现性一般 |
| 壁纸 | 多选 → 加入壁纸队列 → 工具箱 → 壁纸队列 → 应用/裁剪 | 路径长；静态/动态概念需要学习 |
| Pixiv | 工具箱 → Pixiv 归档 → 登录 → 选源/目标 → 扫描 → 归档 | 功能强；默认不显眼，首用门槛高 |
| 更新 | 设置 → 关于 → 应用版本 → 检查更新 | 当前 404 |

### 2.3 IA 问题

#### M-01 · P1 · 相册首屏只有文件夹，没有「全部/最近」

**现状**：`AlbumsScreen` 在根页把媒体按文件夹聚合成 `MediaAlbum`，渲染 `AlbumGrid`；没有「全部照片」这个虚拟相册。`media.isEmpty()` 的空态只给「还没有图片」和「清除搜索」，没有「查看全部/添加文件夹」入口（`AlbumsScreen.kt:288-293`）。时间轴是唯一的全量媒体视图。

**证据**：`SearchLogic.kt:58-71`（按 `folderKey()` 分组）；`AlbumsScreen.kt:288-293`；`docs/screenshots/library.png`（首屏只有 Illustration / Everyday / Travel / Pictures 四个文件夹）。

**影响**：新用户导入一批照片后，打开「相册」看到的是一堆文件夹，而不是照片本身。用户必须先知道照片在哪个文件夹；如果照片散落在多个目录，首屏无法回答「我有多少照片」。这违背了相册类应用的第一预期。

**行业做法**：系统相册和 Google Photos 的首屏是「全部/最近」网格，文件夹/相册是第二层；时间轴是另一种排序，不是唯一全量入口。

**建议**：在相册根页顶部加一个置顶的「全部照片」磁贴（或分段：「最近 / 文件夹」），点击进入按日期排序的扁平网格；保留现有文件夹网格在下方。复用同一个查看器 scope，不新增页面栈。

**工时**：2–3 人日（含空态、滚动位置、选择模式回归）。

#### M-02 · P1 · 图片/视频模式藏在一个「只显示当前状态」的胶囊里，且底栏标签会跟着变

**现状**：顶栏用 `TitleSwitchMark` 显示当前模式（「图片」或「视频」），点击在两者间循环（`VaultTopBar.kt:70-99`）；它取代了页面标题（`VaultTopBar.kt:214-224`）。切到视频后，底栏的「相册」标签和图标会变成「视频」（`AlbumApp.kt:1346-1362`），但底栏项仍是同一个 `MainTab.Albums`。

**影响**：
- 用户看不到另一个选项，只知道「点一下会切换」，不知道会切到什么。
- 底栏出现「视频」标签，用户会以为多了一个「视频」tab；再点它却只是回到当前页，不是切换页面。
- 导航目的地的名称/图标不稳定，违反 Material 3「destinations don't change」的约定（见附录 B-03）。
- 屏幕阅读器读到的是「切换，图片」，没有「图片/视频，二选一」的语义。

**行业做法**：用显式的分段控件「图片 | 视频」；或恢复独立的「视频」tab。无论哪种，底栏标签保持稳定。

**建议**：短期把胶囊改成两段式 segmented control（两个选项都可见、当前项高亮），保留底栏「相册」不变；中期评估是否恢复独立视频 tab。不要用「点一下循环」作为主模式切换。

**工时**：2–3 人日（含底栏/顶栏状态、无障碍、截图回归）。

#### M-03 · P2 · 进入文件夹后底栏消失

**现状**：`barVisible = openedFolder == null && !wallpaperManagerOpen`（`AlbumApp.kt:3245`）。进入文件夹后，底栏整体隐藏，用户只能通过顶栏返回箭头/系统返回退出，才能切到时间轴或工具箱。

**影响**：从「在文件夹里看照片」切到「按时间看」需要先返回；这是高频动作，增加了额外一步。对平板/大屏更明显：底栏消失后没有替代导航。

**行业做法**：顶层目的地常驻底栏；详情页可以全屏，但要有明确的返回与层级。文件夹网格更像「二级列表」，不是全屏详情。

**建议**：文件夹内保留底栏；或者把底栏换成「文件夹上下文条」（返回 + 当前文件夹 + 更多），但不要把导航完全拿走。至少先在文件夹内保留底栏，观察是否影响沉浸感。

**工时**：1 人日 + 回归。

#### M-04 · P1 · Pixiv 作为最强差异化，默认隐藏

**现状**：`pixiv_tab_enabled` 默认 false（`AlbumApp.kt:551`）；Pixiv 只出现在工具箱的「Pixiv 文件归档」卡片（`AlbumApp.kt:331-334`）。README 把 Pixiv 归档与 Tag 检索放在「最突出的差异」第一位（`README.md:19`）。

**影响**：新用户看不到这个功能，产品在货架上失去最强卖点；已配置 Pixiv 的用户也要多点两次才能进。对「为什么不用系统相册」这个问题，首屏没有答案。

**补充（工具箱入口）**：从工具箱点「Pixiv 文件归档」只是把 `selectedTab` 设成 Pixiv（`AlbumApp.kt:3723-3727`），但 Pixiv 默认关闭时底栏 tabs 不含 Pixiv，于是四个 tab 全部未选中；返回时 `selectedTab != primaryTab -> returnToPrimaryTab()`（`AlbumApp.kt:1796`）回到主页而不是工具箱。用户会失去「我在哪」和「怎么回去」。

**行业做法**：把差异化能力放在首屏或默认导航里，用首用说明降低门槛，同时允许用户关闭；不要把它藏在二级工具箱。

**建议**：默认在底栏显示 Pixiv（5 个 tab 仍在 Material 建议范围内），或在相册首屏加一张「Pixiv 归档」卡片；首次进入用一页说明「本地归档、不上传、需要登录」；允许用户在设置里关掉。不要把它藏进工具箱。

**工时**：1–2 人日（默认值、设置迁移、首用说明）。

#### M-05 · P1 · 回收站入口深，删除后没有 Undo

**现状**：删除成功后只弹 Toast「已将 N 项移到回收站」（`AlbumApp.kt:2094-2104`），没有「撤销」或「查看回收站」动作。回收站位于「工具箱 → 文件清理 → 回收站」，是 `CleanupTab` 的第一项（`CleanupScreen.kt:148-151`；工具箱入口 `AlbumApp.kt:330-331`）。

**影响**：误删后用户要在 3 个层级里找回复入口；很多人根本不知道回收站在哪。Toast 一闪而过，没有可操作项，等于只告诉了「东西没了」。这是「有回收站」和「回收站能用」的差别。

**行业做法**：删除后 Snackbar 提供「撤销」；回收站有固定入口/角标；批量删除显示数量与占用。

**建议**：删除成功后用 Snackbar（不是 Toast）提供「撤销」与「查看回收站」；在工具箱/设置给回收站一个固定入口或数量角标；保留期到期前给一次提醒（可选）。

**工时**：1–2 人日（撤销需要保留 staged 记录与恢复回调）。

#### M-06 · P2 · 设置 7 类 54 行，没有搜索

**现状**：设置分 7 类（`SettingsScreen.kt:847-855`），共 54 个 `ToggleRow/ValueRow/ClickableRow`。没有设置搜索、没有「常用/高级」分层，所有选项平铺在二级页。

**影响**：用户找「回收站保留期」「检查更新」「所有文件访问」需要先猜分类；新用户容易被 54 项吓退。对一款强调「可折腾」的应用，设置是能力，但需要有检索与渐进披露。

**行业做法**：设置顶部搜索；按「常用/高级」折叠；危险项单独分组并加说明。

**建议**：先加设置搜索（标题+副标题+关键词），再把「权限/回收站/备份」中的危险项标红并加一句后果说明；不要把 54 项继续增加。

**工时**：1–2 人日。

#### M-07 · P2 · 从设置按返回会回到「主页」，不是上一页

**现状**：`BackHandler` 在设置页关闭子页后调用 `returnToPrimaryTab()`（`AlbumApp.kt:1785-1790`），而 `primaryTab` 是设置里的「主页」（`AlbumApp.kt:1044-1048`），默认「相册」。如果用户从时间轴进入设置，按返回会跳到相册，而不是回时间轴。

**影响**：返回行为与「回到上一页」的直觉不一致；在多 tab 浏览时容易迷路。代码注释明确说这是「home 作为返回落点」的设计，但它和 Android 的返回栈心智冲突。

**行业做法**：返回键遵循 tab 访问栈，根页双击退出；主页设置只决定冷启动落点，不改变跨 tab 返回。

**建议**：维护 tab 访问栈（至少记住进入设置前的 tab），设置根页返回回到上一个 tab；「主页」只用于冷启动与根页连续返回退出，不用于跨 tab 返回。

**工时**：1 人日。

#### M-08 · P2 · 搜索是页内/按类型，没有全局搜索

**现状**：搜索源按 `selectedTab` 切换（`AlbumApp.kt:1250-1256`）：相册搜图片，视频搜视频，时间轴搜当前类型，Pixiv 搜画师/Tag。没有「搜全部照片+视频+文件夹+Pixiv」的入口；搜索不跨类型。

**影响**：用户记得「有一张图」，但不记得在哪个 tab/文件夹；必须逐页搜。文件夹索引是后台加载的，空结果时还会出现全屏 spinner（`AlbumsScreen.kt:261-265`），让搜索显得慢。搜索态还会隐藏图片/视频开关（`titleSwitchWhileSearching` 仅对 Pixiv 为 true，`AlbumApp.kt:3178`），在图片模式搜视频文件名只能退出搜索再切。

**行业做法**：全局搜索 + 类型筛选，结果按类型分组；搜索态保留范围切换，空结果说明当前范围。

**建议**：在相册/时间轴顶栏加「全部」搜索范围，结果按类型分组（照片/视频/文件夹/Pixiv）；保留页内筛选作为二级。先把「搜索中」做成结果区内的轻量状态，不要整页 spinner。

**工时**：3–5 人日（索引与结果分组）。

## 3. 微观问题清单

### 3.1 权限、空态与错误

#### M-09 · P1 · Android 14「部分照片访问」被当成完整授权，没有提示/追加入口

**现状**：`hasImageReadAccess()` / `hasVideoReadAccess()` 在 API 34+ 只要 `READ_MEDIA_VISUAL_USER_SELECTED` 授予就返回 true（`MediaLibraryState.kt:952-966`）。`hasMediaPermission()` 也是「任一权限授予即 true」（`AlbumApp.kt:4601-4603`）。UI 没有「你只允许了部分照片」的横幅，也没有「选择更多照片」的按钮。

**证据**：上述代码；Android 14 部分访问要求应用处理重新选择（附录 B-01）。`docs/rebuild-status.md` 的真机清单也没有这一项。

**影响**：用户选了 10 张照片授权，打开 App 只看到 10 张，会以为「App 把我的照片弄丢了」；没有任何解释或补救入口。这是 Android 14 上最容易产生「数据丢失」误解的路径。

**行业做法**：部分访问时显示持久横幅「仅可访问选中的照片」+「选择更多照片」；重新请求 `READ_MEDIA_IMAGES`/`VIDEO` 并处理 `READ_MEDIA_VISUAL_USER_SELECTED`。

**建议**：增加 `partialAccess` 状态；在相册/时间轴顶部显示一次性可关闭横幅；按钮重新拉起系统照片选择器；`hasMediaPermission` 区分「完整/部分/无」。

**工时**：1.5–2 人日 + API 34 真机验证。

#### M-10 · P1 · 空库没有下一步动作

**现状**：有权限但媒体为空时，相册只显示「还没有图片」；只有 `query` 非空才出现「清除搜索」按钮（`AlbumsScreen.kt:288-292`）。时间轴同样只有文字（`TimelineScreen.kt:146-152`）。没有「添加本地文件夹」「重新扫描」「从系统分享导入」的入口。

**影响**：新用户/清空数据后的用户面对一个死胡同；他必须去右上角「⋮」里找「添加本地文件夹/重新扫描」，或者去设置。空态是产品最好的教学位，现在被浪费了。

**行业做法**：空态给一个主 CTA + 一句解释；例如「还没有照片 / 添加文件夹 / 允许访问」。

**建议**：空态加两个按钮：「添加本地文件夹」（SAF）与「重新扫描」；如果权限被拒，换成「授权访问」；如果只有部分访问，换成「选择更多照片」。

**工时**：1 人日。

#### M-11 · P1 · 扫描失败只有 Toast，英文模式还夹中文；没有重试

**现状**：`MediaLibraryState` 把图片/视频/本地文件夹读取失败收集成中文串（`MediaLibraryState.kt:262-284`），`refreshError` 在界面只被一个 Toast 消费（`AlbumApp.kt:2202-2208`）；英文模式显示 `"Some media could not be read: $message"`，`$message` 仍是「图片读取失败」。相册/时间轴没有错误分支，失败后与「空库」不可区分。

**影响**：用户不知道是「没有照片」还是「读取失败」；Toast 消失后没有痕迹；英文用户看到中英混排。没有重试按钮，只能再下拉一次。

**行业做法**：列表页用持久错误条 + 重试，错误与空态分开；错误文案走资源。

**建议**：把错误建模为 `LibraryError`（类型 + 可重试 + 受影响来源），在列表顶部显示可关闭的 inline banner，带「重试」；空态与错误态分开；错误文案走同一字典/资源，不拼接中文。

**工时**：1–2 人日。

#### M-12 · P2 · 导入的文案说「覆盖」，代码实际是「合并」

**现状**：导入确认弹窗写「导入会覆盖当前的收藏、壁纸与幻灯片队列、排除文件夹和应用偏好设置」（`SettingsScreen.kt:741-745`）；`UserDataBackup.import()` 只是逐 key `put`，从不 `clear()`（`UserDataBackup.kt:64-87`、`102-131`）。本机有、备份没有的键全部保留，实际是并集。

**影响**：用户以为恢复到备份状态，实际保留了旧设备的排除文件夹、删除确认开关等；多设备来回导入会累积状态。更危险的是 `delete_confirmation`、`recycle_bin` 这类安全开关会被备份值静默改写。

**行业做法**：导入前展示将覆盖/保留的键，提供“完全替换/合并”选择。

**建议**：二选一——把文案改成「合并/补齐（同名项以备份为准）」，或在导入时提供「完全替换」并先清空三个 section；校验 `applicationId` 与 UTF-8 字节数（当前用 `raw.length` 与 4 MiB 比较，`UserDataBackup.kt:21,65`）。

**工时**：1 人日。

#### M-13 · P1 · 调小回收站保留期会立即永久删除，没有确认

**现状**：设置页选择「10天/30天/60天/90天」后直接回调 `onRetentionChange`（`SettingsScreen.kt:403-406`），绑定到 `library::purgeExpiredRecycle`（`AlbumApp.kt:3747`），后者立即调用 `cleanup.purgeExpired(retentionDays)` 删除所有超过新期限的私有备份（`CleanupRepository.kt:949-955`）。

**影响**：从 90 天改成 10 天，会一次性永久删除 10–90 天区间内的所有回收站文件，没有数量/占用提示，也没有二次确认。这是设置页里最容易被忽略的破坏性操作。

**行业做法**：保留期变更只影响未来删除，或先预览将删除项。

**建议**：调小时先查询将删除的项数与字节数，弹 `VaultConfirmationSheet` 确认；或改为「新期限只影响之后删除的文件」，避免追溯删除。

**工时**：1 人日。

#### M-14 · P1 · 关闭回收站 + 关闭删除确认 = 一键永久删除

**现状**：`requestDeleteWithConfirmation` 在 `delete_confirmation=false` 时直接调用 `requestDelete`（`AlbumApp.kt:2130-2133`）；`recycleEnabled = !permanent && albumSettings.getBoolean("recycle_bin", true)`（`AlbumApp.kt:2006`）。两个开关独立，没有任何「同时关闭」的警告。

**影响**：用户在设置里关掉两个开关后，任意一次误触（含长按菜单）都会直接永久删除文件，没有最后一道确认。对普通用户，这是不可接受的安全默认。

**行业做法**：永久删除始终二次确认；安全开关不应互相抵消。

**建议**：当 `recycle_bin=false` 时强制保留二次确认（或在设置里把「删除前确认」置灰并解释原因）；批量删除超过 N 项时始终确认；确认文案明确「不可恢复」。

**工时**：0.5 人日。

#### M-15 · P2 · 查看器删除按钮固定写「移到回收站」

**现状**：`ViewerBottomBar` 固定传 `appText("移到回收站", english)`（`MediaViewer.kt:978`），不读取 `recycle_bin` 设置。关闭回收站后，按钮仍说「移到回收站」，实际是永久删除。

**影响**：文案与行为不一致，属于危险操作的错误承诺；用户可能因为「反正能找回」而按下删除。

**行业做法**：按钮文案随实际行为变化，危险动作用危险色。

**建议**：把 `recycleEnabled` 传入 `MediaViewer`/`ViewerBottomBar`，关闭回收站时显示「永久删除」并保持危险色；与确认弹窗标题一致。

**工时**：0.5 人日。

### 3.2 数据与隐私

#### M-16 · P1 · 回收站记录用 `apply()` 保存，且没有孤儿文件对账

**现状**：整张回收站表被 `putString` 到 `cleanup_preferences`，用 `apply()` 异步落盘（`CleanupRepository.kt:1087`）；`loadRecycleEntries()` 对「文件已不存在」的记录直接丢弃（`CleanupRepository.kt:858`），没有提示、没有日志；`filesDir/recycle_bin` 没有「记录 ↔ 文件」的对账/清扫。

**影响**：进程被杀/断电时可能丢记录，而原文件已经删除，回收站副本变成永远看不见的孤儿，占内部存储；反向情形是副本被外部清理后，记录静默消失，用户以为「应用吞了文件」。回收站本应是安全网，现在自己也会漏。

**行业做法**：回收站索引原子写 + 启动对账 + 容量上限。

**建议**：回收站索引改为独立文件原子写（复用 `MediaSnapshotStore.writeAtomically`）或 Room；启动时对账：有记录无文件 → 标记「备份丢失」并允许删除记录；有文件无记录 → 补录或按保留期清理；设置页显示回收站占用与「清理残留」。

**工时**：1–2 人日 + 故障注入测试。

#### M-17 · P2 · 备份没有覆盖动态壁纸队列、最近目标文件夹、回收站与账号

**现状**：`UserDataBackup` 只导出 `album_settings`（除 4 个 deny key）、`album_preferences` 的 6 个 allowlist key、`cleanup_preferences` 的 `excluded_folders`（`UserDataBackup.kt:28-44`）。动态壁纸队列的 `live_wallpaper_queue` / `live_wallpaper_queue_dir`（`ui/WallpaperLauncher.kt:410-414`）、最近目标文件夹 `recent_folders`（`AlbumApp.kt:2262,2346`）、回收站、Pixiv 登录态/Tag 索引都不在导出范围。

**影响**：设置页文案说「收藏、队列与偏好设置」（`SettingsScreen.kt` 备份卡片），用户会以为动态壁纸队列也在内，换机后才发现要重建。回收站与 Pixiv 登录态不导出是合理的隐私取舍，但必须在界面写清楚。

**行业做法**：备份清单明示包含/不包含，关键队列纳入导出。

**建议**：在备份卡片列出「包含/不包含」清单；把 `recent_folders` 与 `live_wallpaper_queue*` 纳入 allowlist（URI 在新设备上可能失效，导入时标记失效项）；明确写「回收站、Pixiv 登录态、Tag 索引不会迁移」。

**工时**：1 人日。

#### M-18 · P1 · 隐私政策说「不上传本地媒体」，但以图搜图会把图片上传给 SauceNAO/ascii2d

**现状**：`ImageSearchActivity.copyForUpload()` 把用户选中的图片复制到 `cacheDir/image_search/`，通过 FileProvider 交给网页表单并自动提交到 `saucenao.com` / `ascii2d.net`（`ImageSearchActivity.kt:358-410`；端点见 `ImageSearchSource.kt:14-24`）。隐私政策只写「媒体只在你主动使用系统分享或打开文件时交给其他应用」（`SettingsScreen.kt:601-607`），没有点名这两个站点，也没有说明图片会被上传。

**影响**：这是应用内除 Pixiv 之外唯一让用户图片离开设备的通道，而且从分享面板一键触发。隐私文案与实现不一致，属于可核对的合规缺口；对「本地优先」的定位也是信任伤害。

**行业做法**：隐私政策逐项披露第三方上传，首次使用前提示。

**建议**：在隐私政策加一段：「使用以图搜图时，所选图片会上传到 SauceNAO / ascii2d，处理受其隐私政策约束」；首次使用前显示一次确认；在搜图页保留「图片将上传」的提示（已有 `:369`，但隐私政策层面仍缺失）。

**工时**：0.5 人日（文案 + 首用提示）。

#### M-19 · P2 · 「退出 Pixiv 登录」没有清理登录进程的 WebView 数据（未验证）

**现状**：登录页在独立进程 `:pixiv_login`，并设置独立 WebView 数据目录 `pixiv_login_v2`（`PixivWebActivity.kt:68-72`）。`clearAuthenticatedSession()` 只在主进程清 `CookieManager` 与 `pixiv_archive` 标志（`PixivArchiveRepository.kt:199-207`）。「更换账号」先清主进程再打开登录页（`CleanupScreen.kt:2428-2436`），但没有任何代码清理 `:pixiv_login` 进程的 WebView 目录/Cookie。

**影响**：代码层面「退出/换号」可能不彻底，旧 Cookie 仍留在应用私有目录；换号时登录页可能直接是已登录状态，导致换号失败。**这是静态推断，未在真机复现，不能断言一定失败**；但当前没有任何清理入口，风险是实打实的。

**行业做法**：退出登录清理 Cookie/WebStorage/缓存，换号强制清空。

**建议**：退出时通过显式 Intent 让 `:pixiv_login` 进程执行 `CookieManager.removeAllCookies()` + `WebStorage.deleteAllData()` + `clearCache(true)`；换号强制清空后再加载登录页；真机验证「退出后重新打开登录页是否仍已登录」。

**工时**：1 人日 + 真机验证。

### 3.3 工程与体验债

#### M-20 · P2 · 死代码 `MainTab.Videos` 仍在，但永远不可达；`AlbumApp` 4,681 行

**现状**：`MainTab.Videos` 仍在枚举里（`AlbumApp.kt:220`），`enabledMainTabs()` 永远排除它（`:256-258`），但 `when (tab)` 里仍保留整套 `MainTab.Videos -> AlbumsScreen(...)` 分支（`:3460-3534`）。`AlbumApp.kt` 4,681 行，13 个文件 ≥800 行；单个 `AlbumApp` composable 约 4,003 行、146 个 `remember`、26 个 `LaunchedEffect`（测量见第 10 章）。

**影响**：视频逻辑有两套入口（`Albums` 的 `albumShowsVideos` 与 `Videos` 分支），修改时容易只改一套；4,000 行 composable 让状态变化影响面过大，配置变更/组合重建的成本高。对用户不是直接可见，但会持续制造回归。

**行业做法**：死代码删除、单文件上限、按页面拆状态。

**建议**：删掉 `MainTab.Videos` 与对应分支（或恢复为真正独立 tab，二选一，不要保留死分支）；按页面把 `AlbumApp` 拆成 `AlbumPage`/`TimelinePage`/`PixivPage`/`SettingsPage` 的 state holder，目标单文件 <1,500 行。先做「滚动条 derivedStateOf」和「Pixiv/底栏」这类低风险拆分。

**工时**：删死代码 0.5 人日；页面拆分 4 人日（分 3 个 PR）。

#### M-21 · P2 · 没有崩溃上报，release mapping 也没有上传通道

**现状**：仓库没有 Crashlytics/Sentry/Bugsnag 等 SDK（`app/build.gradle.kts:163-190` 依赖列表；`grep` 无结果）；release 构建生成 76.39 MiB 的 `mapping.txt`（`app/build/outputs/mapping/release/mapping.txt`），但 CI 不上传，应用内也没有「导出诊断日志」入口。R8 后的线上堆栈无法还原。

**影响**：用户报「闪退/白屏」时只能靠口述；大库、OEM 设备、视频解码等问题无法定位。对一个自发布应用，这会让每次修复都变成猜。

**行业做法**：崩溃聚合 + mapping 上传 + 本地诊断导出（隐私可选）。

**建议**：优先做「本地诊断日志 + 设置页导出」（不引入第三方、不破坏隐私定位）；如果上架 Play，使用 Android Vitals；release CI 上传 mapping.txt 到私有 Release/artifact。不要默认开启第三方统计。

**工时**：2–3 人日。

#### M-22 · P2 · 体积 60.70 MiB，字体占 56.94%，但「全字体子集化省一半」不成立

**现状**：arm64 APK 60.70 MiB；字体压缩 34.56 MiB（56.94%）、LibVLC 20.89 MiB（34.42%），合计 95.10%。旧文档「字体子集化能省一半」不成立：10 款中 8 款本身已接近 GB2312 覆盖，只有 Noto Sans/Serif 两款有显著收益。完整的逐款数字、子集估算与 lite/full 取舍见 10.3。

**影响**：体积是安装转化与低存储设备的第一道门槛；但盲目做「全部字体子集化」投入大、收益集中在前两款，且会引入生僻字回退问题。需要产品取舍，不是纯技术任务。

**行业做法**：按收益/风险排序做体积治理，给用户 lite/full 选择。

**建议**：按性价比排序——① 只子集 Noto Sans/Serif（1.5 人日，APK ≈50.1 MiB，风险最低）；② 做 `lite/full` 双 flavor（无 LibVLC，APK ≈39.8 MiB，明确「AVI/10-bit 需完整版」）；③ 其余 8 款字体按需下载（APK 可到约 26 MiB，但破坏离线首用）。**不要**把 10 款全裁到一级字作为默认方案。

## 4. 设计系统与可用性

### 4.1 颜色与对比度

**现状**：颜色 token 只有 6 个强调色 + 6 个中性色（`Color.kt:5-16`），`Theme.kt` 直接把强调色设为 `primary`（`Theme.kt:14-39`）。Material 3 的 `onPrimary` 默认白色，于是所有「绿底白字」都继承 1.67:1。

**对比度实测（按 WCAG 2.x 相对亮度公式计算）**：

| 颜色 | Hex | 对白底 | 白字对其 | 亮色主题可用性 |
|---|---|---:|---:|---|
| 荧光绿（默认） | `#00E673` | **1.67** | **1.67** | 不可用于文字/白字按钮 |
| 明亮蓝 | `#3D8BFF` | 3.31 | 3.31 | 不达标 |
| 青绿 | `#00C7BE` | 2.12 | 2.12 | 不达标 |
| 活力橙 | `#FF9F0A` | 2.06 | 2.06 | 不达标 |
| 珊瑚红 | `#FF453A` | 3.41 | 3.41 | 不达标 |
| 紫罗兰 | `#AF52DE` | 4.13 | 4.13 | 仍差 0.37 |
| 次要文字 | `#717975` | 4.47 | — | 临界不达标 |

**影响**：底栏选中标签、顶栏模式胶囊、编辑器「完成」、部分强调文字都在亮色主题下不可读。对低视力、强光环境、老年用户是直接的功能损失；对普通用户是「这个绿色有点刺眼/看不清」的品质感损失。

**建议**：
- 拆分 `accent` / `accentText` / `onAccent`，亮色主题的 `accentText` 用深色变体（绿色建议 `#007A3D` 左右，约 5.0:1），`onAccent` 根据填充色计算黑/白。
- 不要把「荧光」用在文字上；荧光色只做小面积装饰/进度，文字用深色。
- 把对比度计算写成单测或脚本，6 个强调色 × 亮/暗 × 文字/填充全部过 4.5:1（大字号 3:1）。

### 4.2 字阶、间距、圆角、动效

**现状（命令统计，源码范围 `app/src/main/java/**/*.kt`）**：

| 维度 | 观察 | 评价 |
|---|---|---|
| 字号 | 133 处 `fontSize = x.sp`，12 个不同值（9/10/11/12/13/14/15/16/17/19/20/28） | `VaultText` 只有 10 个语义角色（`Type.kt:42-52`），实际调用点仍大量硬编码 |
| 圆角 | 91 处 `RoundedCornerShape(...)`，16 个不同值（1/4/5/6/7/8/8.5/10/12/14/16/20/24/28/50%） | 没有圆角 token；同一层级的卡片/胶囊/弹窗半径不统一 |
| 颜色 | 172 处 `Color(0x...)` 字面量 | 主题色之外的硬编码灰/白/黑很多，深色模式容易漏 |
| 间距 | 1,342 处 `.dp` 字面量；`VaultDimens` 只有 14 个值（`Dimens.kt:6-24`） | 没有 4/8 栅格约束；`7dp`、`15dp`、`18dp` 混用 |
| 动效 | 采样到 17 个不同 `tween` 时长（85–900ms）；页面切换 380ms（`AlbumApp.kt:3345`） | 没有动效 token；没有「减弱动效」适配 |

**影响**：单看每一屏都不算差，但跨屏会出现「这个胶囊比那个圆」「这个标题比那个大 1sp」的细微不一致；深色模式下硬编码颜色容易变成白块/黑块。对个人项目是维护成本，对产品是品质感。

**建议**：
- 字阶收敛为 6–8 个角色（Display/Title/Body/Caption 等），禁止新增 `fontSize` 字面量；用 lint/自定义检查拦截。
- 圆角收敛为 4 个 token（4/8/12/16 + full），卡片/胶囊/弹窗各用固定值。
- 间距用 4dp 基准（4/8/12/16/24/32），把 `7dp/15dp/18dp` 这类值逐步替换。
- 动效收敛为 3 个时长（120/200/300ms），并跟随系统「移除动画/动画缩放」；页面切换 380ms 可以降到 240–300ms，减少等待感。

### 4.4 无障碍与设备适配

**量化现状**：
- `contentDescription` 45 处，其中 17 处显式 `null`（含装饰图标，部分是合理的）。
- `.clickable` 92 处，`.semantics` 仅 10 处，`role =` 4 处，`stateDescription` 2 处。
- `AlbumTile`/`PressableMediaThumbnail` 用 `combinedClickable`，没有 `role`、没有选中态语义；`SelectionMark` 的勾选图标 `contentDescription = null`（`MediaTiles.kt:103-110,168-180,185-195`）。
- `combinedClickable` 的 `onLongClick` 传的是空 lambda，真正的长按选择由 `pointerInput` 的 `batchSelectionGesture` 处理（`BatchSelectionGesture.kt:42-92`）；TalkBack 触发的是语义长按，不一定能进入多选（**未真机验证**）。
- 触控目标：多处小于 48dp——回收站还原/彻底删除 34dp（`CleanupScreen.kt:1252-1257`）、幻灯片移除 26dp（`SlideshowQueueScreen.kt:188-195`）、编辑器关闭 42dp（`ImageEditorDialog.kt:730-731`）、视频底部控制行高 46dp 且每项按权重分宽（`Media3VideoPlayer.kt:1649-1659`）。删除类按钮与安全类按钮还紧邻。
- 大量操作是自定义手势：长按多选、拖动批量选择、左右滑切 tab、视频亮度/音量/快进、查看器双击缩放；`GestureHintsSheet` 自己承认「大部分能力藏在长按/双指手势后面」（`GestureHintsSheet.kt:24-26`）。
- 非视频页面固定竖屏（`MainActivity.kt:89`）；`PrototypeViewport(useDeviceViewport=true)` 不再按 412×900 缩放，但仍是单栏手机布局铺满大屏（`MainActivity.kt:121`；`PrototypeViewport.kt:49-61`）。
- targetSdk 36；Android 16 在 `smallestWidth >= 600dp` 的设备上会忽略固定方向/可调整性限制（附录 B-02）。

**影响**：TalkBack 用户无法可靠知道「这是文件夹/已选中/有几个」；自定义手势没有等价按钮；平板/折叠屏看到的是放大的单栏；固定竖屏在 Android 16 大屏上会被系统忽略，行为变成「由系统决定」而不是由设计决定。项目自己的 `docs/rebuild-status.md` 也把 TalkBack/大屏验收列为待做。

**建议**：
- 给 `AlbumTile`/媒体磁贴加 `semantics(mergeDescendants = true)`、`role = Button`、`stateDescription`（已选中/未选中）、`onClickLabel`（打开文件夹/选择）；选中态不要只靠颜色。
- 为手势提供等价按钮：视频的亮度/音量/快进在控制层有按钮（已有部分），查看器缩放提供双击/按钮；批量选择提供「全选」。
- 跑一次 Accessibility Scanner + TalkBack 主流程（浏览→打开→多选→删除→恢复）。
- 用 WindowSizeClass 做 ≥600dp 双栏（左列表/右内容）；先解锁非视频页面的方向，或明确「内容页竖屏、播放器自适应」的策略并测试 Android 16。

### 4.5 深色主题与查看器/编辑器

**现状**：应用有深色主题（`Theme.kt:14-25`），但查看器顶栏/底栏固定白底（`MediaViewer.kt:894,971`），编辑器顶栏/底栏/画布也固定白底（`ImageEditorDialog.kt:726,765`；`Surface(color = Color.White)`）。深色主题用户从相册进入查看器/编辑器会突然全白。

**影响**：夜间刺眼；与「深色主题」承诺不一致。照片查看器用白底有其合理性（中性背景），但需要明确的「始终中性」策略，并在深色主题下降低亮度/提供深色画布选项；编辑器更常用深色画布。

**建议**：把「查看器/编辑器画布」定义为独立的中性表面，不再跟随主题；在设置里提供「编辑器深色画布」；至少让顶栏/底栏跟随主题，画布保持中性。或者明确写「这两个页面始终浅色」并在视觉上做过渡，避免突兀。

### 5.5 发布纪律

1. **一次构建只发一次**：APK、`album-update.json`、SHA-256 必须来自同一次 `assembleRelease`；构建后不再改 `version.properties`。
2. **tag 与版本一致**：`v1.3.65` 对应 `VERSION_CODE=318`；tag 打在发布提交上。
3. **CHANGELOG 顶部与发布说明一致**：用户能看懂「这一版改了什么」，不要只写内部重构。
4. **不把 `app/release/` 当发布源**：它只是本地产物；发布源是 GitHub Release。
5. **发布后 24 小时内**用旧版本做一次真实更新检查；失败就回滚/补资产，不要等用户报。

## 7. 反路线图（明确不做）

> 反路线图不是欠债清单，而是**有理由的边界**。下列事项在当前阶段统一标为 **⏸ 明确暂缓**；只有触发「重新评估条件」时才重新讨论。

| 不做 | 原因 | 重新评估条件 |
|---|---|---|
| 云相册/账号/多端同步 | 与「本地优先、不上传」定位冲突；需要后端、合规、账号体系，个人项目维护不起 | 有明确的付费/团队需求，且能承担隐私与运维成本 |
| 社交/社区/关注/评论 | 不是媒体管理问题；会引入内容审核与运营 | 产品从工具转向社区，且团队具备运营能力 |
| 视频剪辑/转码/NLE | 播放器已经 1,946 行；剪辑是另一个产品；`media3-transformer` 依赖不等于要开剪辑 | 用户明确要求「剪掉片头」这类轻量需求，可做单段裁剪而非 NLE |
| AI 修图/生成/超分 | 模型体积、算力、隐私、成本都与本地优先冲突 | 有可离线、可解释、体积可接受的小模型方案 |
| 第三方统计/广告 SDK | 破坏隐私定位；与「无分析 SDK」的承诺冲突 | 不重新评估（除非产品定位改变） |
| 默认开启的崩溃上报 | 同上；但「本地诊断日志 + 用户主动导出」可以做 | 上架 Play 后使用 Android Vitals（系统级、非第三方 SDK） |
| Google Play 首发 | `MANAGE_EXTERNAL_STORAGE` 与相册类应用的 Play 政策不匹配；当前自分发 | 移除/可选化该权限，改用 MediaStore + SAF，完成 Play 政策申报 |
| 一次性大重构（全量 ViewModel/DI/DataStore） | 40k 行、无 UI 测试，重写风险高于收益；strangler 模式已在进行 | 关键页面已有 UI 测试与回归，或单文件 >8,000 行 |

## 9. 按 App 实际情况的专项

### 9.1 国际化：双语可用，但架构仍是「手写字典 + 内联三目」

**现状**：
- `res/values/strings.xml` 只有 4 条（`app_name`、`live_wallpaper_description`、两个分享入口名）；`values-en` 只有 2 条（`strings.xml`）。
- 界面文案主字典是 `AppLanguage.kt` 的 `APP_ENGLISH`：242 个 key（去重后 239，存在「媒体」「进入多选」「重复图片…」3 个重复 key）；437 处 `appText(`（含定义）。
- 仍有 234 处 `if (english)`、24 处 `if (isEnglish)`、11 处 `if (appLanguage == "English")` 的内联三目；这些字符串不在字典里，测试也覆盖不到。
- `TranslationCoverageTest` 只扫描 `appText("字面量")`，注释明确说「A call whose first argument is an expression cannot be resolved here」（`TranslationCoverageTest.kt:21-23`）。所以 `appText(someVariable)`、`if (english) "..." else "..."` 都不受保护。
- `localeFilters = ["en", "zh"]`（`app/build.gradle.kts:51-55`），系统层只有中英；应用内语言是运行时切换，不触发资源重建。
- 英文模式下错误串仍可能是中文：`refreshError` 是中文拼接（M-11）。

**影响**：英文版会出现漏翻/中英混排；第三种语言无法加入（要改437 处 （含定义） + 234 个三目）；翻译无法交给外部译者；系统分享面板的应用名在英文系统上仍是「相册」（`values/strings.xml` 的 `app_name` 没有 `values-en` 覆盖）。

**建议**：分两步——① 把所有 `if (english)` 三目收敛到 `appText()`，让覆盖测试能扫到；② 迁移到 `values/strings.xml` + `values-en`，用 `stringResource`/`context.getString`，开启 `MissingTranslation`。第二步会触碰大量 composable，排在 IA 稳定之后（Phase 2）。短期至少给 `app_name` 加英文资源，避免桌面图标名不一致。

**状态**：🟡（双语可用，架构未达标）。

### 9.2 隐私与权限：本地优先的承诺基本成立，但有三处需要补

**做得好的部分（应保留）**：
- 无账号、无云同步、无统计/广告 SDK；`allowBackup=false`，云备份与设备迁移都排除（`AndroidManifest.xml:52-54`、`res/xml/backup_rules.xml`、`data_extraction_rules.xml`）。
- 更新检查只接受 HTTPS、禁止 userInfo/fragment、响应体限制 256 KB（`AppUpdateChecker.kt:41-64,178-184`）。
- 删除默认进应用私有回收站，空间不足时逐项让用户决定（`AlbumApp.kt:2031-2041`、`UnbackedDeleteSheet`）。
- Pixiv 登录在独立进程，WebView 开了 JS 但无 `addJavascriptInterface`（`PixivWebActivity.kt:68-102`）。

**需要补的三处**：
1. **权限过宽/申请时机**：`MANAGE_EXTERNAL_STORAGE`、`MANAGE_MEDIA`、`SYSTEM_ALERT_WINDOW` 都在清单里（`AndroidManifest.xml:5-22`）；首启自动跳「所有文件访问」「媒体管理」（T3）。`MANAGE_EXTERNAL_STORAGE` 对 Play 上架是高风险（附录 B-06）。建议把它降级为可选/仅自分发渠道，核心路径走 MediaStore + SAF。通知权限已在 v1.3.67 从清单移除。
2. **以图搜图上传未披露**：M-18；隐私政策必须点名 SauceNAO/ascii2d。
3. **Pixiv 退出/换号清理不彻底（未验证）**：M-19；至少补登录进程的 Cookie/WebView 清理，并真机验证。

**另外**：
- FileProvider 暴露整个 `cacheDir`（`file_paths.xml:3` 的 `path="."`），实际只用 `external_media/` 与 `image_search/`；建议收窄到子目录（风险有限，但符合最小暴露）。
- `MANAGE_MEDIA` 与 `MANAGE_EXTERNAL_STORAGE` 的「已开启」状态在设置页显示为 Toggle，点击会跳系统设置；开关的视觉语义与「跳转」行为不完全一致，建议改成「状态行 + 前往设置」。
- 没有仓库级 `PRIVACY.md`；隐私政策只在设置弹窗内。自分发可以接受，但上架/分享时需要可链接的页面。

**状态**：🟡（定位成立，披露与权限边界需补）。

### 9.3 本地媒体兼容与文件操作

**现状**：MediaStore（图片/视频）、SAF（授权目录）、物理路径（`MANAGE_EXTERNAL_STORAGE`）三条通道并存；LibVLC 作为 Media3 解不动的 AVI/MPEG-PS/10-bit H.264 回退（`VideoFrameFallback`、`VlcMedia3Player`）。这条“多通道 + 双引擎”是应用能处理真实本地库的原因，也是复杂度的来源。

**风险**：
- 覆盖写入的删除顺序（T2）是最高风险；复制后没有回读校验（`MediaFileOps.kt:14-35`），`VerificationFailed` 枚举未使用。
- 回收站记录非原子/孤儿（M-16）；关闭回收站 + 关闭确认（M-14）。
- 改名改后缀时 `relativePath` 为空可能不写 `RELATIVE_PATH`，落到 MediaStore 默认目录，把文件挪出原文件夹（`MediaRepository.kt:348-350,363`）；**未真机验证**，建议补测试。
- 没有“文件操作失败”的持久日志，用户只能看到一次 Toast；建议把最近 20 条操作结果放进设置页的诊断区。

**建议**：把“文件操作”当成一个独立的质量域：覆盖/移动/重命名/回收站四条路径各有一组失败注入测试；所有失败都给“源/目标是否保留”的明确结论；诊断日志可在设置页导出。**状态**：🟡。

### 10.2 性能风险

#### P-01 · P1 · 每次冷启动可能触发两次全量扫描（高置信静态推断）

**证据**：`LaunchedEffect(library.permissionGranted)`（`AlbumApp.kt:2166-2168`）在首次组合时执行，`refresher.request(Startup, granted=true)`；`MediaLibraryState.refresh()` 开头把 `permissionGranted = granted`（`MediaLibraryState.kt:222`），状态从 false→true，导致 effect 重启并再次请求。`RefreshCoordinator.request()` 没有同源去重（`RefreshCoordinator.kt:18-31`）。权限回调本身也会再请求一次（`AlbumApp.kt:1937-1939`）。

**影响**：启动时两次 MediaStore 全量查询 + 归一化/排序 + 两次缩略图调度；47k 图库单次查询/排序是数百 ms 量级（未实测），纯属重复 CPU/IO、发热与电量。首帧来自快照，不直接拖慢首帧，但会延长后台忙碌。

**建议**：只在权限值真的变化时请求；`RefreshCoordinator` 对同 source 正在跑/排队时合并。验收：冷启动 logcat 只出现一条 `after scan`（`ThumbnailRepository.logStats`）。

#### P-02 · P1 · 编辑器打开时在主线程加载 10 款字体（原始 60.42 MiB）

**证据**：`ImageEditorDialog.kt:157` 的 `LaunchedEffect(context) { EditorTypefaceRegistry.initialize(context) }` 默认在主线程；`EditorTypefaceRegistry.initialize()` 对 `EditorFont.entries` 全量 `ResourcesCompat.getFont`（`ImageEditorEngine.kt:57-64`），无“已初始化”短路。APK 内 10 款 TTF 原始 60.42 MiB，需解压/解析。

**影响**：首次打开编辑器可能主线程阻塞（低端机数百 ms 到数秒，未实测），并常驻 native 内存。这比缩略图更直接地影响“点编辑要等一下”的体验。

**建议**：`withContext(Dispatchers.IO)` + 已初始化短路；改成按需加载（导出只用到用户选中的 1–2 款，预览侧 Compose `Font()` 本来异步）。

#### P-03 · P1 · 12MP 导出峰值内存可达 96–144MB

**证据**：`ImageEditorEngine.kt:211-218` 允许 12,000,000 像素（ARGB ≈48MB）；`geometryBitmap` 无条件 `Bitmap.createBitmap` 全尺寸复制（`:264-269`，即使旋转=0/无翻转）；导出/调整/overlay 各再复制；马赛克申请 result 48MB + `pixels` IntArray 48MB + `output` IntArray 48MB（`:749-756`）。Manifest 无 `largeHeap`。

**影响**：按 48MB/份估算，低内存设备导出 12MP 图峰值可达 96–144MB，有 OOM 风险；`runCatching` 可能吞掉 OOM，用户只看到“导出失败”。

**建议**：无旋转/翻转时直接返回 source；按 `Runtime.maxMemory()` 动态下调导出上限；马赛克按 block 流式处理；及时 recycle。

#### P-04 · P2 · 缩略图 key 在每次重组时做 SHA-256 + 16 次 `String.format`

**证据**：`MediaTiles.kt:246` 把 `ThumbnailRepository.peek(...)` 作为 `produceState` 的 `initialValue` 参数，每次重组都会求值；`ThumbnailRepository.cacheKey()` 每次拼字符串、`MessageDigest.getInstance("SHA-256")`、`digest.take(16).joinToString { "%02x".format(it) }`（`:400-404`）。`placeholderBrush` 也在重组中新建 Brush（`MediaTiles.kt:361-369`）。

**影响**：可见格滚动时持续产生临时字符串与哈希对象，增加 GC 压力；未实测 jank，但属于纯浪费。

**建议**：手写 hex 查表（微基准约 45× 差异，仅数量级参考）；按 `(uri,size,gen)` 缓存 key；`placeholderBrush` 用 `remember(item.id)`。

#### P-05 · P2 · 大库媒体快照全量重写，49k 图约 14.6 MiB

**证据**：`MediaSnapshotStore` 用 `JSONObject` 组装后 `toString()`，`writeAtomically` 走 fsync（`MediaSnapshotStore.kt:44-91`）；`MediaLibraryState` 只要快照签名变化就整份重写（`:360-382`）。按单条 JSON 约 313B 外推，49k 图约 14.6 MiB。

**影响**：大库每次内容变化写 ~15 MiB + fsync；内存里 JSONObject 树 + String 同时存在，可能与缩略图缓存叠加。未实测。

**建议**：改流式 `JsonWriter` 或 SQLite/Room 增量 upsert；写盘加低电量/充电条件。优先级低于 P-01/P-02。

### 10.3 容量与瘦身

**事实**：
- 字体 34.56 MiB（56.94%）+ LibVLC 20.89 MiB（34.42%）= 95.10%；dex 4.34%；其余资源/assets 0.42%。
- 10 款字体中 8 款只有 7,016–9,431 字形，已接近 GB2312 覆盖；只有 Noto Sans/Serif 两款子集化有显著收益。
- 只裁 Noto 两款：估算 APK **≈50.1 MiB**；10 款全裁到 GB2312：**≈48.2 MiB**；裁到一级字：**≈38.2 MiB**（生僻字/日文假名回退）；无 LibVLC 的 lite 版：**≈39.8 MiB**；字体按需下载：**≈26 MiB**（破坏离线首用）。
- `useLegacyPackaging=true` 让下载 60.70 MiB、安装约 113.6 MiB（估算）。

**建议排序**：
1. **只子集 Noto Sans/Serif**（1.5 人日，APK ≈50.1 MiB，风险最低，系统字体可兜底）。
2. **lite/full 双 flavor**（2.5 人日，lite ≈39.8 MiB，明确 AVI/10-bit 需完整版）。
3. **其余 8 款按需下载**（3 人日，APK ≈26 MiB；只在明确接受“离线首用需联网”时做）。
4. **不要**把“10 款全裁到一级字”作为默认：收益没有想象中大，回退/日文假名问题需要逐款真机验证。
